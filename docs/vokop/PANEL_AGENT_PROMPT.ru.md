Ты работаешь в моём существующем форке 3x-ui. Реализуй совместимость с клиентом Vokop, не создавая новый форк панели и не заменяя уже реализованные функции. Vokop находится в https://github.com/remzone/vokop. Источник истины — закреплённый коммит Vokop и документы `docs/vokop/CONTRACT.ru.md`, JSON Schema/примеры в `docs/vokop/`; при споре сверяйся с кодом клиента в `vokop/files/usr/lib/subscription/vkturn.uc`, `management/client.uc` и `tools/vokop-fetch/`.

## Границы и порядок работы

1. Прочитай AGENTS.md, инструкции репозитория, текущую архитектуру, миграции и тесты. Работай в отдельной topic-ветке от указанной мной ветки. Не меняй защищённые ветки, не force-push и не публикуй без разрешения, предусмотренного моими инструкциями.
2. Аудируй существующие VK TURN, VLESS, подписки, пользователей, тарифы/сроки оплаты, Telegram-бота, прокси Telegram API, конфигурацию Xray и планировщики. Переиспользуй их; не создавай параллельную базу пользователей и платежей.
3. Сначала сопоставь реализованные возможности с контрактом Vokop. Создай краткий план с конкретными классами/таблицами/маршрутами и рисками миграции. Затем реализуй, а не останавливайся на плане.
4. Не запрашивай реальные ключи в чате. В тестах только фиктивные секреты и локальные mock-серверы. Не изменяй живую панель, сеть VPS, firewall, реальные токены и аккаунты без отдельного разрешения.
5. Контракт Vokop версии 1 не расширять молча. Если нужная функция отсутствует у клиента, явно опиши ограничение; не изобретай endpoint/command и не заявляй совместимость без проверки.

## Реализовать

### A. Сервер и профиль транспорта

- Устройство Vokop использует VLESS через локальный VK TURN sidecar. Сервер VK TURN принимает транспорт и перенаправляет соединения на разрешённый VLESS inbound Xray.
- Найди и адаптируй уже существующую поддержку VK TURN. Если её нет, создай управляемую серверную интеграцию на основе закреплённого исходника `cacggghp/vk-turn-proxy`, соблюдая лицензию и безопасность. Не маскируй отсутствие серверного транспорта одним JSON-генератором.
- В профиле нужны peer host/port VK TURN сервера, HTTPS VK call link, число потоков 1–16 и VLESS UUID существующего пользователя.
- Peer port — не порт Xray. Внутренний VLESS inbound нельзя автоматически открывать всему интернету. Не переделывай чужие REALITY/xhttp/TCP настройки. Роутер версии 1 не принимает произвольные параметры TLS/REALITY/xhttp.
- Не выполняй конфигурационные строки пользователя через shell. Разрешённые аргументы запуска формируй типизированно, проверь адреса/порты/ссылки, редактируй Xray через существующий сервис панели.

### B. Подписка Vokop

- Добавь отдельный формат выдачи `vokop.subscription.v1`, не ломая старые форматы `/sub` и QR-ссылки. Выделенный путь `/sub/vokop/{opaque_token}` допустим; клиенту передают полный конечный HTTPS URL без редиректов.
- Все поля и границы точно из контрактной схемы. Генерируй чистый JSON UTF-8, не Base64, `Content-Type: application/json`. Не добавляй «полезные» поля, иначе строгий клиент отвергнет документ.
- Храни монотонную `revision` для подписки. Любое изменение профилей/таймстемпов увеличивает revision; одинаковая revision должна возвращать одинаковое семантическое содержимое. GET не должен каждый раз менять issued_at при той же revision.
- Стабильные уникальные profile ID; timestamps — UNIX seconds; срок конверта максимум 31 день и не больше срока entitlement. Для долгих тарифов обновляй конверт заранее с новой revision.
- Максимум 16 профилей на источник, без дубликатов; не выдавай пустой profiles как механизм отзыва. Большие наборы потребуют явно согласованного разделения.
- URL формируй из явно настроенного публичного HTTPS адреса/префикса панели, не из hostname контейнера/ВМ и не из недоверенного Host-заголовка. Не используй значение вида se-13205 вместо внешнего адреса. Ссылка в Telegram и UI должна быть идентичной при одинаковом профиле.
- Не выдавай VLESS UUID, VK ссылки или токены пользователям чужой подписки. URL подписки является секретом; не писать его полностью в access/application/error логи.

### C. Устройства и локальное разрешение

- Добавь сущность устройства, связанную с владельцем/подпиской, и админский интерфейс создания/отзыва/ротации device token. Device ID генерируй из совместимого набора букв, цифр, `_`, `-`, до 64 символов.
- Device token криптографически случайный, уникальный, не админский token панели. Покажи только один раз по HTTPS, храни безопасный проверочный хеш; при утечке можно отозвать конкретное устройство.
- Выдай владельцу инструкцию локального размещения token в `/etc/vokop/management.token` с правами 0600 и настройки `/etc/config/vokop_management`. Не включай управление удалённо. Включение только локальное, по умолчанию disabled.
- Настройка подписки и включение управления независимы. Удаление device token не отзывает VLESS UUID автоматически, если не выбран явный отдельный сценарий.
- Не добавляй root/SSH-доступ, не открывай порт на WAN и не собирай аппаратный fingerprint без отдельного согласия.

### D. Очередь команд и ACK

Реализуй точные публичные клиентские маршруты относительно panel base URL:

- `GET /api/vokop/v1/devices/{device_id}/commands?after=N`
- `POST /api/vokop/v1/devices/{device_id}/ack`

Оба проверяют `Authorization: Bearer <device_token>` и привязку к device_id.

GET возвращает `200` с `{"schema":"vokop.commands.v1","commands":[]}` или максимум 16 строго возрастающих команд `{id,type,expires_at}`. Командный ID положительный, до 2^53−1, не переиспользуется. Отфильтруй ID <= after. Срок новой команды максимум 24 часа, учти небольшое расхождение часов. Не добавляй аргументы, payload произвольного конфига или shell.

Только три команды:
- `refresh_subscriptions`;
- `restart_vkturn`;
- `disable_vkturn`.

ACK принимает `{"schema":"vokop.ack.v1","results":[{"id":1,"status":"applied"}]}`; статусы applied/failed/expired/rejected. Храни результат транзакционно и идемпотентно. Повтор идентичного ACK успешен; чужой ID/устройство или попытка изменить финальный результат отвергается. Возвращай 204 либо 200 после записи. Очередь и ACK переживают рестарт панели. Не помечай команду выполненной только потому, что GET её выдал.

Админские действия создания команд защищены существующим auth/RBAC и CSRF, пишут безопасный аудит. Device token не может пользоваться админским API. Реализуй ограничения частоты и длины JSON; не принимай лишние/дублирующиеся ключи в контрактных payload.

В интерфейсе различай «поставлена», «выдана», «подтверждена», «ошибка», «истекла». ACK applied не означает здоровый туннель. При потере питания действие может повториться; не обещай exactly-once.

### E. Оплата, срок и отзыв

- Сохрани существующие тарифы/ручное подтверждение оплаты/напоминания и остальные функции бота. Их правила не менять ради Vokop.
- Истечение/отзыв должно отключать соответствующий VLESS UUID на стороне Xray. Нельзя полагаться только на недоступность подписки или добровольный клиентский watchdog.
- Выдача 403 или пустой подписки не удаляет ещё действующий кеш. При срочном отзыве блокируй серверный доступ; команду disable_vkturn можно отправить дополнительно.
- disable_vkturn sticky: после продления удалённый restart не снимет блокировку. Объясни владельцу требуемое локальное включение и не обещай автоматического восстановления после оплаты.
- Недоступность панели не должна превращаться в произвольное изменение LAN/DNS/Wi-Fi роутера.

## Тесты и результат

Добавь backend unit/integration и контрактные тесты, которые используют **реальную схему и реальные валидаторы Vokop** закреплённого коммита, либо однозначно отдели тесты схемы от клиентского runtime-теста.

Обязательные сценарии: правильная подписка; изменённая та же revision; rollback revision; expired/слишком долгий TTL; malformed/лишние/дублирующиеся поля; чужая подписка; закрытая учётная запись; ротация/отзыв token; IDOR между устройствами; повторный GET/ACK; потеря ответа ACK; рестарт панели; истёкшая/неизвестная команда; отсутствие произвольного shell; CSRF/RBAC; публичная ссылка с внешним адресом и префиксом пути; старые форматы подписок/бот/оплаты без регрессий.

Проверь сборку, линтеры, миграции на копии БД, существующий test suite и новый mock-панель ↔ клиент сценарий. Отдельно укажи, что реальный VK call/VPS/OpenWrt не проверен, если их не было. Не выдумывай passed для пропущенных тестов.

Сдай: код, миграции и откат, схему хранения устройств/очереди, API OpenAPI/примеры, инструкцию настройки сервера и устройства, список проверенных команд и результатов, оставшиеся ограничения.
