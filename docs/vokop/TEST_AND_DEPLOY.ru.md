# Vokop: сборка, стенд и восстановление

## Состояние проверки

Этот документ описывает **процедуру**, а не утверждает, что она уже выполнена. Проверяйте отчёт для конкретного коммита. Сборка клиентского Go-бинарника ≠ сборка `.ipk/.apk` ≠ установка пакета ≠ работа VK TURN на настоящем OpenWrt.

Нет проверенной универсальной совместимости «везде, где работает AmneziaWG». AmneziaWG и Vokop используют разные зависимости. База Forkop требует **OpenWrt 24.10+**, nftables и подходящие ucode/fs/uci, sing-box и другие компоненты. Старые OpenWrt/сторонние прошивки требуют отдельного переноса. Выбирайте пакеты строго по версии прошивки, target/subtarget и package architecture; имя CPU само по себе недостаточно.

| Уровень | Что можно подтвердить | Что он не подтверждает |
|---|---|---|
| Unit/contract tests на host | Валидацию и часть логики | Поведение OpenWrt/procd/nftables |
| Linux Go cross-build | Компиляцию для GOARCH | Совместимость конкретного SDK/ядра |
| OpenWrt SDK build | Сборку ipk/apk и зависимости | Реальный VK звонок и маршруты |
| Router smoke test | Работу конкретной версии/устройства | Все другие модели/прошивки |

Архитектуры-кандидаты транспорта: amd64, arm64, armv7, 386, mips/mipsle softfloat, mips64le, riscv64. Это список кандидатов, **не список протестированных роутеров**. Ориентируйтесь на ограничения Go builders соответствующего OpenWrt SDK.

## Сборка из исходников

Используйте официальный SDK именно вашей версии OpenWrt с feeds packages/luci. Go host toolchain должен удовлетворять `transport/vk-turn-proxy/go.mod` (на момент реализации 1.25.5+). SDK старого выпуска может содержать слишком старый Go: не утверждайте совместимость только по наличию рецепта.

Репозиторий необходимо добавить в SDK **целиком**: recipes используют соседние `transport/` и `tools/`. Не копируйте один Makefile без исходников.

1. Закрепите коммит `remzone/vokop`, сохраните его SHA.
2. В SDK настройте локальный feed `src-link vokop /absolute/path/to/vokop` в `feeds.conf`; обновите/установите обычные официальные feeds согласно документации SDK.
3. Установите рецепты `vokop`, `luci-app-vokop`, `vokop-fetch`, `vokop-vk-turn` из локального feed; проверьте зависимости в menuconfig. Применимость этих шагов к конкретному SDK должна быть подтверждена сборкой, а не предположением.
4. Соберите frontend по lockfile в `fe-app-vokop` и его скрипту `build`. Не используйте `format`/`ci` как read-only lint: upstream `ci` форматирует исходники.
5. Соберите пакеты SDK, сохранив полный build log и manifest. Не называйте Linux ELF-бинарник OpenWrt-пакетом.
6. Сохраните SHA256 файлов и матрицу: версия OpenWrt, target/subtarget, package architecture, SDK SHA, Vokop SHA, результаты сборки.

Нельзя запускать старый upstream installer, скачивающий Forkop/Podkop, как установщик Vokop. Не применять `curl | sh`. До появления проверенного релиза используйте только собственные собранные пакеты. Выключенные/непроверенные workflow не являются доказательством успешной CI.

## Перед установкой на стенд

Получите и сохраните вывод `ubus call system board`, данные архитектуры менеджера пакетов, свободное место/RAM, состояние WAN/DNS и текущий способ доступа. Не публикуйте приватные данные отчёта.

- Сделайте резервную копию OpenWrt и конфигураций текущего VPN/DNS. Сохраните её **вне роутера**.
- Проверьте физический доступ/failsafe. Для устройства, доступного только по Wi-Fi, не меняйте LAN/Wi-Fi/DHCP и заранее определите способ восстановления доступа.
- Изучите `CONFLICTS` рецепта: Vokop не рассчитан на одновременную установку с Podkop/Forkop и рядом DNS/proxy пакетов. Удаление конфликтующего пакета — отдельное осознанное действие. Не удаляйте его без сохранения конфигурации и плана отката.
- Не импортируйте UCI-конфигурацию Forkop простым переименованием без проверки миграции. Сначала сравните настройки и отключите применение маршрутизации.
- Пакеты с kernel-зависимостями должны соответствовать конкретной прошивке. Не используйте force-depends для «лечения» несовместимости.

## Порядок проверки

1. Установите локально собранные пакеты через менеджер данной прошивки, оставив Vokop и управление выключенными. Проверьте LuCI, наличие бинарников и отсутствие самовольных изменений WAN/LAN/DHCP.
2. Создайте тестовую подписку в адаптированной панели с корректными внешними HTTPS URL, VLESS UUID и VK call link. Не кладите её в публичный Git. Время роутера должно быть синхронизировано.
3. Добавьте URL в интерфейсе Vokop. Проверьте валидацию и группы **до** включения маршрутизации.
4. Включите локально нужную секцию. Проверьте loopback-only listeners, процессы procd, сгенерированный sing-box config и marked WAN bypass `0x08000000`. Наличие процесса — не доказательство туннеля.
5. Проверьте end-to-end HTTPS через VLESS/VK TURN, затем маршруты LAN-клиента. Сравните ожидаемые direct/proxy назначения, DNS и IPv6. Не должно быть рекурсивного перенаправления VK API, TURN, DNS bootstrap и панели в собственный туннель.
6. Только затем настройте отдельное управление панелью: token локально в файле 0600, device ID/base URL, enabled. Не вставляйте секрет в shell history/логи; используйте безопасную передачу файла.
7. Проверьте команды refresh/restart/disable и ACK. Убедитесь, что disable сохраняется после restart, перезапуска панели и роутера. Никакая команда не должна менять Wi-Fi/LAN/админский доступ.
8. Проверьте короткую тестовую expiry, отзыв UUID сервером, остановку транспорта, обновление revision, потерю панели, недоступный TURN, неверный сертификат, CAPTCHA и перезапуск питания. Старый рабочий конфиг не должен заменяться недопустимым.
9. Проверьте сохранение обычных подписок и групп Forkop. HTTPS-only/no redirects является намеренным ограничением Vokop: старые HTTP/redirect URL нужно заменить конечными HTTPS URL, а не выключать TLS-проверку.

### Обязательная матрица отрицательных сценариев

- JSON с лишними/повторными ключами, shell-метасимволами, слишком большим телом, неверным типом числа, повтором profile ID.
- Откат revision и изменённое содержимое при той же revision.
- Истёкший feed, недоступная панель, HTTP/redirect/self-signed delivery, invalid device token.
- Повтор command/ACK, неизвестный тип, чужой device ID, power loss около записи ACK state.
- Коллизия loopback портов, отказ установки socket mark, dynamic TURN relay, DNS TCP fallback, IPv6/другой VPN со своими policy rules.
- Health-check отказ при живом процессе: статус должен быть degraded, а не healthy только по PID.

## Восстановление

Сначала отключите управление локально и остановите `vokop-management`; это прекращает новые удалённые команды, но не возвращает маршрутизацию автоматически. Затем отключите основной Vokop через локальный интерфейс/сервис и остановите VK TURN. Используйте штатный stop/restore путь, не удаляйте вручную чужие nftables-таблицы и не сбрасывайте всю сеть.

Для локального снятия **только** sticky VK TURN запрета после проверки причины: удалите `/etc/vokop/vkturn-disabled`, затем перезапустите `vokop-vkturn`. Это сознательное повторное разрешение владельца; панель его делать не может. При отключённом/истёкшем профиле само по себе оно не восстановит доступ.

Если доступ/интернет не восстановился, верните сохранённую конфигурацию известным способом восстановления OpenWrt. Универсальной безопасной команды восстановления для всех моделей нет. Сначала докажите этот путь на стенде, затем переносите изменения на рабочий роутер.

Не обещать автоматический откат по потере интернета без отдельно проверенной реализации. Проверка JSON и атомарная запись файла не равны полноценному transactional network rollback.
